# 独立审计报告

审计对象为 Bohn et al. 2021 *Reinforcement Learning of the Prediction Horizon in Model Predictive Control* 的重建工程、当前 vehicle/pendulum 证据链，以及后续标记为 `IMPROVED` 的 latency-tree、true-variable-H 和 risk/value selector 研究路线。

本轮审计快照起点为 commit `6a1c80b218f6a11499f99523829905018aeb0eb1`，脏差异哈希为 `5c0fa5d9f567c991a11f9a3cee624c00762a1b82146f880adf40b6a3194abeb4`。快照记录的活动实验为 `20260929T140824_fbdb657d`，PID `87311`，状态为 `running`。因此，下面的结论以已读取的文件和原始证据为准；活动中的 v10 是否已经产生最终结果，在本轮可见证据中没有得到确认。

审计结论是：当前项目不能宣称完成 Bohn 2021 的 ORIGINAL 复现，也不能宣称 `IMPROVED` 方法达到最终科学验收。作者核心代码、SAC 梯度训练路径、AHMPC 机制和部分 raw 训练结果确实存在；但原始配置和原始测试集缺失，实验配置由本地重建，且应用了多个语义修正。当前 vehicle 研究主要是有限候选搜索、监督式风险模型和开发集分支诊断，并非原论文 SAC。倒立摆的当前恢复库存仍显示 seed1 中断、seed2 缺失。H10/H15 的局部计算机会存在，但原始 AHMPC 实现保持固定 H50 NLP 维度；v10 的离线 selector 评估没有把实际 kNN 查询时间计入在线决策时间。最终 sealed test 没有被本轮审计访问，故没有最终测试结论。

## 原始方法、作者源码和车辆/倒立摆进度

作者源码定位是清楚的。`runtime.py:6-22` 将本地路径固定到 `research_artifacts/bohn2021_reproduction_2026-09-17/sources`，并导入 `LetMPCEnv`、`SAC` 和 `AHMPCPolicy`。`SOURCE_MAP.md:7-14` 还记录了作者 stable-baselines、gym-letMPC 和 do-mpc 的具体来源定位。这部分支持源码 provenance。

重建配置不是作者原始配置。`configure.py:23-81` 自己构造 inverted pendulum 和 vehicle 的动力学、奖励、约束、observation 及 MPC 参数。vehicle 的环境 `end_on_constraint_violation` 为空，见 `configure.py:64-71`；本地 `runtime.py` 又用碰撞距离检查补上终止和 penalty。这是一个影响成功率和 constraint 计数的行为变化。pendulum 也由本地逻辑重新检查位置和角度约束。不能把这些修正后的结果直接称为原作者环境结果。

倒立摆模型和成本的具体形式在 `configure.py:27-45`，vehicle 的 unicycle 动力学、追踪成本和三障碍 observation 在 `configure.py:50-62`。这些内容可以支持数学重建审计，但不能替代缺失的作者原始 JSON、场景 bank 和实验启动参数。

作者原始 AHMPC 的 horizon 机制已经核实：所有状态动力学、stage cost 和软硬约束都放在最大 horizon NLP 中，通过 `hend` 屏蔽超出 H 的项，见 `controllers.py:681-719`。vehicle 的障碍物 forecast、距离约束和噪声生成在 `controllers.py:773-885`。这说明原论文机制的核心可追踪，但也直接解释了为什么 action H 的减少不必然降低 `opt_x` 维度。

旧 `paper_defaults` 中至少有一个可核实的 SAC 训练实例。`pendulum_rl_s0.log:155` 的观测值为：

- `steps=15000`
- `updates=14745`
- `train_episodes=223`
- `weights_changed=true`
- `evaluation_frozen=true`
- `test_episodes=10`
- `reproduction_level="core author code with reconstructed experiment configuration"`

这不是纯参数网格搜索；`sac.py:297-300` 和 `:326-335` 确实建立了 optimizer train op，`sac.py:372-383` 每次 update 采样普通 replay 和 32-step MPC replay。训练开始前的随机探索路径在 `sac.py:473-500`，`learning_starts`、随机 action 和 stochastic policy 的关系也在代码中明确。`run.py:131-137` 设置了 `learning_rate=3e-4`、`gamma=.97`、`tau=.005`、`learning_starts=100`、`train_freq=1`、`gradient_steps=1`、`train_mpc_value_fn=True` 和 `use_mpc_vf_target=False`。

但这并不等于完整的收敛证据。初始化只以 `initial_hash` 记录，代码没有保存完整初始参数分布、梯度范数、terminal-value 权重曲线或独立停止准则。训练是固定步数执行，`run.py:174-180` 每 2,500 步保存 checkpoint，最终保存 model；没有基于验证性能的预先冻结 checkpoint 选择证据。

奖励和成本也必须分开报告。`configure.py:69-74` 定义 reward 为负的 performance cost 加 horizon computation penalty；`run.py:132-137` 对 pendulum 使用 `reward_scale=.6`、vehicle 使用 `.3`；`sac.py:504-512` 再将环境 reward 除以 `reward_scale` 后放入 replay。因此日志中的 positive cost、环境 reward 和 SAC critic target 不是同一尺度。terminal Bellman target 使用实际 n-step reward 和 `gamma ** n_step`，见 `sac.py:262-265`；本地 replay sampler 又由 `runtime.py:109-137` 修正 terminal inclusion 和 ring-buffer boundary。所有报告需要同时给出原始 cost、scaled reward、constraint penalty、solver failure 和 terminal bootstrap mask。

倒立摆当前恢复库存与旧 `paper_defaults` 证据不能拼接。库存 raw 明确显示当前 `pendulum_s0` 完成、`pendulum_s1` 中断、`pendulum_s2` 缺失；旧目录虽然存在 `pendulum_rl_s0`、`pendulum_rl_s1`、`pendulum_rl_s2`，但本轮没有读取其完整 raw manifest 和结果。车辆旧目录也存在 fixed-H 和 RL seed 目录，但没有在本轮逐一核实其成本、安全、失败和 terminal provenance。因此，当前两任务的三 seed 完整性不成立。

## 训练、终端价值和失败机制

原 SAC 训练有真实梯度路径，但项目同时包含多条完全不同的改进方法：

- ORIGINAL reconstruction：`run.py` 调用作者 SAC，包含 policy/Q/value 和 MPC terminal value 训练。
- latency-tree：有限深度决策树、CE 搜索、训练内候选选择，协议见 `docs/protocols/bohn2021_latency_tree_2026-09-26.md:11-19`。
- v6/v8/v9：用 paired branch outcomes 形成风险标签和监督式 selector。
- v10：kNN/RBF 风险/value refit，明确没有 RL gradient training，见 `vehicle_true_variable_horizon_risk_value_knn_refit_v10.py:1-14`。

这几类结果不能合并为一个“学习了 prediction horizon”的结论。

当前训练协议对 exploration 有明确代码路径，但诊断仍不完整。`sac.py:473-500` 在 `learning_starts` 前随机采样，之后调用 stochastic policy；`run.py` 默认 `ent_coef='auto'`，对应 entropy coefficient optimizer，见 `sac.py:267-273`。尚未充分记录每个 seed 的实际 entropy coefficient、action/H 分布、探索后期的 H 覆盖率和 terminal-value replay 的有效样本数。对 horizon 学习尤其需要报告 H=5…50 的 visitation，而不能只看最终 policy。

失败和截断处理在代码上有一定可追溯性。`sac.py:530-539` 把自然 steps termination 与 constraint/solver termination 区分开，并决定是否 bootstrap。`run.py:158-164` 累积 solver failures 和 episode termination。可是当前 raw 诊断没有把以下原因完全拆开：

1. NLP 初始点或 warm-start 造成的 solver failure；
2. 碰撞或物理约束造成的真实失败；
3. fixed-size masked NLP 在短 H 下仍然使用长维度造成的数值行为；
4. terminal value 对短 H 的错误外推；
5. reward scale 和 constraint penalty 使 critic 偏向安全但高成本行为；
6. 随机场景和探索动作造成的自然失败。

倒立摆日志中的 constraint termination 和 solver failure 同时出现，说明这不是只靠平均 reward 可以解释的问题。后续训练必须记录每步 solver status、恢复尝试、迭代次数、constraint 类型、bootstrap mask 和 terminal-value target，而不是只记录 episode total cost。

当前 terminal-value 训练也有两个边界。第一，`run.py:131-137` 训练 MPC value function，但 `use_mpc_vf_target=False`；第二，评估时 `run.py:64-70` 通过替换权重支持 value/no-value 对照，但本轮没有读到所有 seed 的数值对照。必须把 terminal value 当作独立实验因子报告，包括：

- no terminal value；
- 当前 32-step shared terminal；
- independently trained per-H terminal；
- 是否使用 target terminal network；
- terminal 权重初值、最终值和范数；
- terminal replay 的有效 n-step 分布；
- fixed-H 与 adaptive-H 是否使用相同 terminal 来源。

## 场景分布、观察充分性和分支继续

当前风险研究已经证明，H10 并非完全没有机会。v8c raw 中 selected rows 的固定 H10 decision saving 明显低于 H15 的部分决策时间，但风险差异巨大。例如第一类 catastrophic row 的 H10 physical 为 `272.8320`，H15 physical 为 `17.5339`，差值为 `255.2982`；第二类差值为 `247.8665`，见 `vehicle_true_variable_horizon_risk_probe_acquisition_v8c_flexible_state_count_20260929T1320Z/raw.json:16-105`。这说明短 H 的局部 solver opportunity 与 catastrophic continuation cost 可以同时存在。

但这些不是自然随机 bank 的代表性估计。v8 先从候选池按 `fresh_high_heading...`、`low_clearance`、`lower_stress` 等角色挑选 case，见 `vehicle_true_variable_horizon_risk_probe_acquisition_v8.py:215-288`；然后在 H15 trace 的风险窗口中挑选 branch state，见 v8c `:62-128`。这个设计适合发现机制，不适合估计总体发生率。

v1 的 branch protocol 有一个正确的因果约束：先执行 H15 Stage A trace，写出 `selected_state_manifest`，再执行 H10/H15 Stage B branch outcome，见 `vehicle_true_variable_horizon_fresh_source_confirmation_v1_runner.py:8-17`。`build_state_profile_rows` 也在 branch outcome 之后计算 H10 beneficial label，见 `:203-259`。不过，选择窗口、风险分数和 case role 仍然改变了 branch state 的分布。

v10 的 deployable feature 集包括 14 维 observation、上一 pose、`branch_step`、`branch_state_slot`、`stage_a_trace_risk_score` 及其派生项，见 `vehicle_true_variable_horizon_risk_value_knn_refit_v10.py:118-154`。这有两个需要单独核实的问题：

- `stage_a_trace_risk_score` 是否能在实际 H 决策前由在线历史计算，还是只存在于离线 H15 trace selection？
- `branch_state_slot` 和 `branch_step` 是否是部署时可知的时间/历史变量，还是编码了实验人员选择窗口的信息？

v10 的协议声明 candidate policy 不读取 scenario group/window metadata，见 `:424-426`，这是积极约束；但代码只检查 bank id 不含 `validation` 或 `test`，见 `:104-115`，没有在这里证明跨 bank 的 state hash 去重、历史训练场景去重和 role selection 去重已经完成。需要一个独立的 feature timestamp 和 row provenance 审计。

分支继续也存在实现差异。true-variable-H smoke 的 `reset_env_to_branch` 会先运行一次上游 reset，再直接覆盖 branch state、shifted TVP、simulator state，并重置 controller，见 `vehicle_true_variable_horizon_case5_smoke_v0_runner.py:616-671`。代码记录了 `branch_state_distance_after_reset`，这是必要的诊断；但本轮没有读到其最终数值，因此不能确认分支初始状态与原轨迹一致。直接状态覆盖还需要验证 simulator history、object noise、goal、TVP forecast 和 controller warm-start 是否与自然闭环继续相同。

## 固定 H、terminal opportunity、选择预算和验证污染

正式协议写得比当前 raw 结果完整。`REPRODUCTION_PROTOCOL.md:7-9` 要求三 training seeds、H=5…50、validation64、sealed128，并要求固定 terminal、共用 terminal、失败和选择规则完整报告。改进协议又规定所有 fixed arm 和 adaptive candidate 具有相同 frozen terminal、solver retry 和 failure accounting，见 `docs/protocols/bohn2021_latency_tree_2026-09-26.md:29-36`。

问题在于“协议已声明”与“每个 arm 已有可审计 raw 结果”之间仍有差距。本轮没有看到：

- 全部 H=5…50、三个 seed 的完整 fixed-H episode rows；
- 每个 H 的 terminal-value 权重来源和训练预算；
- fixed-H 选择是否使用了单独 validation bank；
- adaptive policy 和 fixed-H comparator 是否使用相同 horizon dimension、相同 solver retry 和相同 reset；
- 每个失败 arm 是否保留 raw failure，而不是只保留通过的候选；
- 选择后是否重复使用了已经暴露的 validation64。

`paper_defaults` 目录中的 fixed-H 文件只能说明曾经有这些 jobs，不能代替上述证明。任何只报告 H25/H30 或只报告一个 fixed baseline 的比较都不满足强基线要求。

当前 validation64 已被用于 IMPROVED latency-tree 的正式 shard。协议历史记录 shard11 已完成但仍把整个路线标为 `IMPROVED`、不是 ORIGINAL、不是 final-test evidence，见 `REPRODUCTION_PROTOCOL.md:124-137`。因此：

- 已暴露的 validation64 可以用于诊断和历史记录；
- 不能在继续选择模型、特征、terminal 或阈值后把它称为独立最终确认；
- sealed128 仍然必须保持关闭，直到代码、模型、规则、预算、固定 H baseline 和审计全部冻结。

本轮没有发现 sealed test 已被访问的证据。相反，多个完成标记都记录 `sealed_test_accessed=false`。这是一项通过的治理检查，但不等于实验已经可以进入 final test。

## Solver、NLP 维度和真实 timing

原始 masked AHMPC 的维度问题已经由代码确认。`controllers.py:728-740` 只改变 `hend` 和 TVP，不重建 `n_horizon`；因此 H10 和 H15 仍然共享 H50-sized NLP。`case5_smoke` 的输入检查也要求先确认既有 evidence 是 fixed-size，见 `vehicle_true_variable_horizon_case5_smoke_v0_runner.py:267-275`。

项目随后编写了真实 variable-dimension controller。`make_true_horizon_env` 通过 `config_kw={"mpc": {"params": {"n_horizon": true_horizon}}}` 构造真正的 H10/H15 controller，见 `vehicle_true_variable_horizon_case5_smoke_v0_runner.py:540-601`。该 smoke 计划为两个 branch state、H10/H15 各一条，共 4 个 episode、最多 600 control steps，见 `:85-95`。它属于 `IMPROVED` 实现诊断，不能当作原论文实现。

公平 timing 还需要补足四个方面：

1. **warm-start 和缓存**：`AHMPC.reset` 会调用 `set_initial_guess()`，见 `controllers.py:721-725`。true H10/H15 controller 的缓存、initial guess 和 solver history 是否与 fixed-size arm 相同，尚未由 raw timing 证明。
2. **整步边界**：正式协议要求从特征读取、selector、所有 solver retry、可行性检查到决策完成都计入，见 `docs/protocols/bohn2021_latency_tree_2026-09-26.md:21-27`。v10 离线汇总没有 selector timing。
3. **配对和随机顺序**：协议规定固定随机顺序和两次重复，但本轮没有读取最终 raw timing 表来确认所有 arm 都按同一顺序、同一 branch state 配对。
4. **CPU interference**：协议承认宿主 WSL 调度是限制，但没有看到 CPU pinning、load snapshot、thermal state 或 host-level interference audit。registry 的 wall time 和 RSS 不足以排除干扰。

因此，当前可以说“已有局部分支数据支持 H10 计算机会假设”，不能说“已经测得 adaptive H 的部署决策时间优势”。

## 统计不确定性、有效样本量和安全门

v10 的 nested LOBO 结构比直接在全部开发行上选择一个配置更好，但其有效样本仍然很小。协议使用四个 development banks：`fresh_v0`、`fresh_v1`、`fresh_v2`、`fresh_v8c`，见 `vehicle_true_variable_horizon_risk_value_knn_refit_v10.py:417-430`。四个 bank 才是外层独立单位；同一 branch 的多次 repeat、同一 case 的多步控制和 median outcome 都不能当作新的独立场景。

v10 配置数为 43,740。对四个 bank，代码实际进行：

- 全局 LOBO：`43,740 × 4`；
- 每个 outer bank 的 inner selection：`43,740 × 3 × 4`；
- 每个 outer bank 一次 outer evaluation。

也就是约 `699,844` 个配置级评估，尚未把每次 kNN 邻居计算成本作为独立预算。如此大的选择空间在四个 bank 上容易得到不稳定的赢家，即便使用 nested outer evaluation，也不能把“nested zero catastrophic FP”解释为部署风险接近零。

v6/v10 的安全定义还存在口径差异：

- v6 row label 用 `max(2.0, 5% × H15 physical)` 作为 tolerance，见 `vehicle_true_variable_horizon_risk_tree_representation_v6.py:155-164`；
- v1 的 row gate 也使用 `max(2.0, 0.05 × abs(H15 physical))`，见 `vehicle_true_variable_horizon_fresh_source_confirmation_v1_runner.py:220-235`；
- v8c raw 的 catastrophic diagnostic threshold 使用 `max(2.0, 0.25 × H15 physical)`，例如 threshold `4.3835` 和 `3.3702`，见其 raw `:16-105`。

这些是不同用途的诊断阈值，但当前报告必须明确区分，不能把不同 threshold 下的“zero catastrophic”合并。

`eval_choices` 以 aggregate physical delta 和 tolerance sum 计算 physical gate，见 v6 `:293-312`。如果 baseline H15 自身不安全，某些 H10 failure 不会被同样定义为 H10 catastrophic；因此最终安全门必须同时报告 H15 baseline 是否安全、H10 safe_all、solver failure、constraint episode 和 physical delta，不能只报告一个 aggregate gate。

项目正式协议要求 10,000 次 paired bootstrap，并保留 seed-level 结果，见 `docs/protocols/bohn2021_latency_tree_2026-09-26.md:38-42`。本轮读取的 v10 代码没有执行这一统计步骤，也没有输出零事件风险上界。最终需要按 case/bank 聚类 bootstrap，保留 seed 为层级因素，并报告 rare catastrophic event 的置信上界。

## 基础设施、恢复和证据 provenance

证据 provenance 的设计有优点：

- `runtime.py:6-13` 固定本地 source snapshot；
- `run.py:148-155` 保存 config hash、test-bank hash、observation dimension、terminal dimension 和 fidelity 分类；
- v10 `:417-430` 保存输入 hash、split、feature policy、budget 和 validation/test access flags；
- v10 `:516-521` 写出 backup request、raw、summary 和 completed marker。

但活动 worker 在 backup 之后启动，且当前 v10 仍在 snapshot 中运行。snapshot 记录 backup commit 为 `6a1c80b...`，而 v10 运行 ID 为 `20260929T140824_fbdb657d`。v10 自身的 raw/completed、registry 和文档更新必须在完成后重新做外部 backup，不能只依赖启动前的 backup。

恢复历史表明 orchestrator 有实际风险：

- shard02 曾错误使用 modern interpreter，因 TensorFlow 缺失而在无 control step 前失败，之后才用 legacy interpreter 重试；
- shard05 和 shard07 的审计 v1 因 registry schema 不同而失败，v2 才修复；
- registry 中同一科学 shard 因运行失败、恢复、审计修复形成多个 experiment ID。

这些失败被保留是正确的；但在继续正式实验前，registry schema 应统一接受 `commit_sha`/`git_commit`、`episodes_exact`/`episodes` 等等价字段，并由 metadata-only contract test 覆盖。否则审计器本身会产生 false negative，浪费正式预算并增加恢复复杂度。

当前没有证据显示 sealed test 被误读，也没有证据显示 v10 使用 validation64。v10 的 `load_all_rows` 只拒绝 bank id 中含 `validation` 或 `test` 的输入，见 `:104-115`；这不足以证明历史场景 hash 去重完成。应把 exact row hash、base state hash、source candidate index、case role 和 branch state manifest 纳入输入审计。

## 竞争性解释及区分方法

| 竞争解释 | 当前支持证据 | 最小区分实验 | 何时被证伪 |
|---|---|---|---|
| 可部署 observation/history 不足以识别 H10 catastrophic risk | v8c 中安全/灾难分支物理差距很大；v10 仍在尝试用 pose、observation、history 和 risk proxy 表示 | 在未用于 v10 选择的新 development bank 上，固定 same H15 trace，加入真实在线 clearance、上一 solver status、短历史窗口和 forecast summary；按 bank 留出 | 丰富特征后仍在外层 holdout 产生 catastrophic H10 FP，则单纯 observation insufficiency 不能解释全部失败 |
| terminal value 或 reward objective 把短 H 推向错误 continuation | SAC 训练 MPC terminal value，使用 32-step replay；当前 v10 没有重新训练 terminal value | 同一 dynamics、scenario、solver 和 seed，比较 no-value、当前 shared terminal、per-H terminal、target-terminal 四组；只在 training/development bank 选择 | oracle terminal 或 per-H terminal 仍产生相同 catastrophic branches，则 terminal objective 不是主因 |
| 主要瓶颈是固定 H50 NLP，而不是 horizon policy | 作者 AHMPC 明确使用 `hend` mask；case5 预检查记录 fixed size | 对同一 branch state 做 fixed-size H10/H15 与真实 `n_horizon=10/15` 的 paired timing，记录 `opt_x_size`、solver attempts、warm-start 和 whole decision | true H10 与 H15 维度相同或没有 solver saving，则 true-dimension路线不能支撑速度假设 |
| 机会只存在于定向风险探针，遇到自然场景就消失 | v8c 按风险 role/window 选状态；只有少量 bank | 预先冻结未按 outcome 选择的 stratified fresh bank，按 case 留出，禁止继续挖掘 holdout | fresh bank saving 消失或只在 targeted cases 存在，则原 selector 只能算开发诊断 |
| selector 查询和 CPU interference 吃掉 MPC saving | v10 没有测 kNN query；协议承认宿主调度限制 | 在单独无并发 CPU 上随机化 paired order，测 feature、kNN/tree、solver、recovery、reset 边界，报告 gross/net | 加入 selector overhead 后 whole decision saving 小于 5% 或重复间方向不一致，则部署速度解释被证伪 |
| H10 catastrophic 实际由 solver recovery/failure 而非物理 continuation 造成 | pendulum 日志同时出现 constraint termination 和 solver failures；v8c raw 记录 solver counts | 重复相同 branch state，分别记录每次 solver status、retry、iteration、initial/final failure，并做 no-retry diagnostic | 物理成本差异在 solver 全部成功时仍存在，则 solver-only解释不足；若只在失败时出现，应优先修 solver/recovery |
| fixed H15 不是公平或足够强的 baseline | 当前 raw 没有闭合全 H grid 和 per-H terminal provenance | 在同一 terminal policy、同一 seed 和同一 bank 上完成 H5…H50 全网格，再独立完成 per-H terminal opportunity track | 某个未报告 H 或 per-H terminal 显著优于 H15，则现有 H15比较不够强 |

## 给 GPT-5.5 的优先执行任务

### 1. 先封存 v10 结果和活动实验 provenance

**假设/目的：** v10 可能在审计期间完成或留下部分输出；任何重启都会破坏当前 frozen experiment 的可解释性。

**最小干预：**

- 让 `20260929T140824_fbdb657d` 在安全边界结束；
- 保留所有 `raw.json`、`summary.md`、`completed.json`、protocol、stdout/stderr、registry 和 continue state；
- 记录最终 PID、exit status、source hash、输入 bank hash、selector evaluation count；
- 完成后进行一次覆盖这些文件的外部 backup。

**冻结 split/budget：** 不新增 simulation、control step、training episode、validation64 或 sealed128。

**接受规则：**

- 成功、失败或中断都必须有唯一 experiment ID；
- `completed.json` 与 registry 的 `status`、`exit_status`、budget 和 source hash 一致；
- v10 结果必须继续标记为 development `IMPROVED`，不能写入 ORIGINAL 结果表。

**失败规则：** 如果 raw 不完整、输出被覆盖、registry 与文件 hash 不一致，v10 只能作为失败/不完整诊断，不能用于下一阶段选择。

### 2. 完成 ORIGINAL reconstruction inventory，再决定补训

**假设/目的：** 目前至少有作者核心代码和一条真实 SAC 训练记录，但缺少完整的三 seed、两任务、checkpoint 和 terminal provenance。

**最小干预：**

对现有 artifact 做 metadata-only inventory，逐项登记：

- task、seed、训练步数；
- initial/final model hash；
- 实际 gradient update count；
- terminal-value 权重 hash、训练开关和 checkpoint；
- reward scale、batch size、buffer size、entropy coefficient；
- train/holdout bank hash；
- failure、constraint、solver failure 和 truncation denominator。

优先使用已有文件；只有缺失的 pendulum seed1/seed2 或 vehicle seed 才按冻结 ORIGINAL protocol 补训。补训必须沿用 `run.py` 的明确 `--steps`；现有 s0 日志显示的基准是 15,000 steps。

**冻结 split/budget：**

- 训练 bank 只使用已登记 training bank；
- 不读 validation64 或 sealed128；
- 每个缺失 seed 最多 15,000 steps；
- 不因早期曲线改变步数、奖励或选择规则。

**接受规则：**

- pendulum 和 vehicle 各有 seed0/1/2 的可审计训练 manifest；
- 每个 seed 的权重确实改变，gradient count、terminal replay count 和失败分类齐全；
- 不满足时，报告“ORIGINAL training incomplete”，不补充成功叙述。

**可证伪点：** 如果所有现有 checkpoint 都不能提供初始权重、terminal source 或 bank hash，就不能把补训结果与旧 artifact 合并，必须重新冻结 ORIGINAL campaign。

### 3. 建立完整强 fixed-H 基线和 terminal opportunity track

**假设/目的：** adaptive-H 的任何改善都必须相对于完整 H grid 和合理 terminal 机会比较。

**最小干预：**

冻结两条独立基线：

1. **common-terminal track**：相同 frozen terminal、相同 solver retry、H=5,10,…,50；
2. **per-H-terminal opportunity track**：每个 H 使用独立且明确 provenance 的 terminal value，训练/选择预算与被比较的 adaptive arm 对齐。

每条 track 都保留所有 H，包括失败和明显差的 H。H25/H30 可以作为历史参考，但不能预先当作最佳固定 H。

**冻结 split/budget：**

- 三个 training seeds；
- development bank 用于训练和初步选择；
- validation64 只在代码、terminal、模型和选择规则冻结后使用一次；
- sealed128 继续封存；
- 不从已经暴露的 latency-tree validation64 重新选择新的 ORIGINAL 模型。

**接受规则：**

- 每个 H、每个 seed、每个 terminal track 都有 raw episode rows；
- 报告 performance cost、computation cost、constraint cost、solver failures、initial/final failures、success 和 truncation；
- 固定 H 提名必须由预先冻结的安全和成本规则产生；
- 若 common-terminal 与 per-H-terminal 的最佳 H 不同，必须分别报告，不能合并。

**需要科学选择的部分：** per-H terminal 是为了公平比较还是为了测“固定 H 最佳机会”，两者的 scientific meaning 不同，必须在正式 protocol 中明确，不能运行后选择解释。

### 4. 完成 true-variable-H 的最小 timing 诊断

**假设/目的：** 如果真实 `n_horizon` 不降低 NLP 维度，继续优化 selector 没有速度基础。

**最小干预：**

在已有 case5 branch state 之外使用一个未参与 selector 选择的小 development block，成对运行：

- fixed-size H50-masked H10；
- fixed-size H50-masked H15；
- true `n_horizon=10`；
- true `n_horizon=15`；
- fixed true H15 comparator。

每一对使用相同 branch state、TVP、goal、object noise、terminal 权重和 solver retry。随机化 arm 顺序，重复两次，记录 warm-start/cache 状态。

**冻结 split/budget：**

- 最小 4 个 branch states；
- 每个 state 至少包含 H10/H15 两个 true-dimension arm 和 fixed-size 对照；
- 约 24 episodes、最多 3,600 control steps；
- 不训练、不读 validation、不读 sealed test。

**必须记录：**

- `opt_x_size`、NLP variable/constraint dimension；
- 每一次 solver attempt、iterations、success、recovery；
- reset、feature、selector、solver 和整个 decision wall time；
- CPU load、host、线程环境和随机顺序；
- gross 与扣除 logging 后的 net time。

**接受规则：**

- true H10 的 `opt_x_size` 明显小于 H15；
- solver time 和 whole decision time 在两个重复中都下降；
- 物理、安全、solver failure 不恶化；
- selector overhead 计入后仍至少有 5% development saving，10% 才能称为 strong diagnostic。

**失败规则：** 维度不变、saving 不稳定或只在 solver 失败时出现，立即停止“短 H 即更快”的路线，转向 solver/terminal 或 scenario design 诊断。

### 5. 对 risk/value 表示做一次未挖掘 fresh-bank 实验

**假设/目的：** v8c 的 opportunity 可能来自定向风险状态；v10 的 nested LOBO 可能在四个 bank 上仍然过拟合。

**最小干预：**

冻结一个新的 development bank，在生成 manifest 后才确定 H15 Stage A branch state。按 case 而非 row 分层，覆盖：

- 高/低 heading；
- 高/低 clearance；
- 长/短 trajectory；
- 早期/中期/后期 branch；
- 不同 obstacle forecast regime。

每个 branch state 执行 paired H10/H15 continuation，保留两次重复。训练 bank、fresh holdout bank 和最终 validation bank 必须按 case/bank hash 分开。

**冻结 split/budget：**

- 8 个 fresh cases；
- 每 case 2 个 branch states；
- Stage A H15 8 episodes；
- Stage B `8 × 2 × 2 = 32` episodes；
- 总计约 40 episodes、最多 6,000 control steps，具体上限在 protocol 写入后冻结；
- 不读取 validation64/sealed128。

**模型比较：**

- observation/pose/history；
- 加在线 clearance/forecast summary；
- 加 `stage_a_trace_risk_score`；
- scenario group/window 仅作为 leakage diagnostic，不得作为部署 feature；
- feature permutation 和 leave-one-family-out。

**接受规则：**

- 选定配置只能使用 training banks；
- fresh holdout 上零 catastrophic H10 false positive；
- physical gate 为真；
- 加入实际 selector overhead 后 decision saving 至少 5%；
- 每个 case、每个 bank 单独报告，不能只给 aggregate。

**失败规则：** 如果只有 scenario metadata 或 targeted risk role 能通过，而 deployable feature 不能通过，则结论是存在 distribution shift 或表示不足，禁止进入 validation rollout。

### 6. 若风险表示失败，再做 terminal/reward cause experiment

**假设/目的：** catastrophic H10 可能来自 terminal value、reward scale 或 continuation objective，而不是 selector 表示。

**最小干预：**

在 ORIGINAL/IMPROVED 之间保持清晰边界，固定 dynamics、scenario、solver 和 seed，只改变 terminal/value 因子：

- no terminal value；
- 当前 32-step shared terminal；
- independently trained per-H terminal；
- 可选的 target-terminal 对照。

每个因子至少三个 seeds；记录 gradient count、MPC value loss、terminal weight norm、n-step count、entropy、Q/value scale、H distribution 和 failure type。

**冻结 split/budget：**

- 只用 training/development banks；
- 每个 seed 15,000 steps，预算在协议中写死；
- 不读取 validation64/sealed128；
- 不根据中途结果删除失败 seed。

**接受规则：**

- 某个 terminal/objective 因子在未用于选择的 development holdout 上降低 catastrophic rate；
- fixed-H H15 cost 和安全不恶化；
- 训练曲线、terminal target 和 failure diagnostics 能解释改善。

**可证伪点：** 如果 terminal ablation 对 catastrophic rate 没有影响，而 true-dimension timing 或 fresh-bank split 改变结果，则 terminal objective 不是主瓶颈。

### 7. 重新冻结 validation 和最终 sealed test 门槛

只有前述 baseline、训练、timing、risk representation 和 audit contract 完成后，才进入最终阶段。

**冻结内容：**

- commit、环境、配置、source hash；
- 三 training seeds；
- fixed-H comparator 和 terminal source；
- adaptive policy/checkpoint；
- selector feature、阈值、拒绝/回退规则；
- validation/test bank hash；
- timing order、CPU 运行规则和预算；
- 统计代码和报告模板。

**validation：**

- validation64 只做最终 fixed-H 选择和准入；
- 如果已暴露的 validation64 继续被开发调参，必须新建独立 validation bank；
- 报告逐 seed、逐 case、逐 bank 结果；
- 采用协议规定的 paired bootstrap，并以 case/bank 为独立单位。

**sealed test：**

- 只有 validation 全部通过后才执行 sealed128；
- sealed test 只执行一次冻结模型；
- 任一 validation safety、cost、timing 或 solver gate 失败，sealed test 保持关闭；
- test 结果不能反过来选择 H、terminal、feature 或 checkpoint。

验收标准必须继续使用 `docs/protocols/bohn2021_latency_tree_2026-09-26.md:38-42` 中登记的门槛，不因负结果放宽。

### 8. 修复 registry、backup 和恢复 contract

**最小干预：**

- 统一 `commit_sha`/`git_commit`、`episodes_exact`/`episodes`、`test_accessed`/`sealed_test_accessed` 等 schema；
- 对每个 metadata-only audit 先运行 contract test；
- 保留 failed run、partial output 和 recovery artifact；
- 每个新 formal evidence 前完成外部 backup；
- 在 EC2 计划结束前，即 `2026-10-25 18:30 Asia/Shanghai` 前，完成分块外部恢复备份；
- 不进行 IAM 或基础设施升级；
- 不恢复 mobile robot joint K/H 研究。

**接受规则：**

- supervisor、registry、completed marker、raw hash 和 external backup proof 相互一致；
- orchestrator 不重复执行已完成 job；
- 中断后可以从明确 checkpoint 恢复，且不会把部分 branch 当作完整 bank；
- backup proof 覆盖 source、protocol、raw、registry、stdout/stderr、状态和恢复说明。

## 需要更大科学选择或不可用证据的事项

以下问题不是常规脚本修复可以自行决定的：

1. **严格 ORIGINAL 复现是否仍然可行。** 原始配置和原始测试集没有在当前证据中找到；只能选择“作者核心代码加重建配置”的可复现实验，不能把它宣传为精确论文复现。
2. **per-H terminal 的科学含义。** 如果它用于公平 fixed-H baseline，就必须和 adaptive terminal 分开；如果它用于测固定 H 的理论机会，也必须单独标记为 opportunity upper bound。
3. **已暴露 validation64 是否继续可用。** 如果任何模型、feature、terminal 或 selector 在其结果上被选择，必须重新建立独立 validation；这个决定不能由审计者用已有结果替代。
4. **true-variable-H 是否仍属于研究目标。** 它改变了原作者固定 H50 mask 的 solver 构造，因此即使通过，也只能作为 `IMPROVED` 方法。
5. **缺失的作者数据和完整 checkpoint。** 没有原作者 test bank、原始训练配置、完整 seed manifest 或 terminal weights 时，无法从代码审计推导出原论文数字。
6. **外部 backup 的真实可恢复性。** 当前本地证据只能证明项目记录了 backup commit 和请求，不能代替对外部 release asset、下载哈希和恢复演练的独立验证。

本报告是开发阶段的独立建议和风险审查，不是 final acceptance，也不是 sealed test 授权。快照可能在活动 worker 运行时发生并发变化；v10 的最终结果、完整 vehicle raw performance、完整 pendulum 三 seed 训练和任何 sealed/final-test 结果均不在本轮结论范围内。
