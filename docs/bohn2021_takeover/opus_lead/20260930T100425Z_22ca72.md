## 三、当前真正的阻塞项：目标重构从未被验证过一次

这是唯一挡在 24 次预算前面的东西，我复核后认为风险判断成立，且缺陷比上一轮报的更具体：

`v34d...v0.py:208–212` 的接受门是
```
rel = |stage_lterm_total + gamma_pow_H_terminal − solver_objective| / max(1, |solver_objective|)
```
但 `reconstruct_stage_and_terminal_v34d()` 本身有几处我**在源码里直接确认**的疑点（均未修）：

1. **末端节点索引**：`:196` 取 `opt_x_num_unscaled["_x", int(h), 0, 0]`（第 h 个节点），而 do-mpc 的 stage 求和末端用的是 `-1`。`:175/:178` 同样混用 `k+1, -1` 与 `k, -1`。这不是风格问题，会直接改变 terminal 处的 vf 取值。
2. **缺项**：`:172–194` 只累加 `lterm_fun` 与 `vf_fun`，全文件搜 `epsterm` **零匹配**（我已用 search 确认），也没有 input regularization 分项。而 `:156–160` 自己就承认 `input_regularization_separate_component_available: False`、`stage_lterm_may_include_slack_or_other_terms: True`。如果 solver 目标含这些项，`rel` 会系统性偏大——**看起来像"重构失败"，其实是缺项**。
3. **残差检查可能空转**：`:678` 的 `residual_vs_bounds` 在 `:968` 被传入 `mpc.opt_x_num` / `opt_x_lb` / `opt_x_ub`，而底层 solver 实际用的是 `lb_opt_x/ub_opt_x`，**不是同一对象**；且 `None` 被当作通过。所以"residual ≤1e-5"这个门可能永远不真地否掉任何东西。
4. **终端系数表 schema**：`:848` 的 `parse_terminal_coeff_csv` 接受 `linear/quadratic/bias`，而新表列名是 `linear_coeff/quadratic_coeff/bias` 且首列是 `terminal` → 会得到**空系数字典**，即 vf 静默退化成零。这个我无法在本轮确证（未读到 CSV 本体与 `:848–872` 全段），标记为**高优先级假设**，任务 B 的输出必须能区分它。

关键点：**v0e 预检证明不了任何一条**。它只证明了"四参数 `vf_fun`/`lterm_fun` 调用可用"，从没算过一次 `|J_recon − J_solver|`。也就是说，这个接受门**只会在 24 次预算花掉之后首次暴露**——这正是不能直接开跑的理由。
