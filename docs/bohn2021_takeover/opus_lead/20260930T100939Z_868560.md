## 二、错位 #1：residual 为 `None`（工程，先修，零预算）

链条很清楚：

- `residual_vs_bounds`（`v34_objective_basin_solver_probe_v0.py:678–682`）在 `lo.size != x.size` 时返回 `None`。传入的是 `getattr(mpc, "opt_x_lb", [])`（`v34:968`）。
- v34g 的 `install_full_capture`（`v34g:128–152`）把额外数组写成 `"complete_" + attr` 前缀，所以确实应该有 `complete_opt_x_lb`。
- 但 `raw.json` 里没有任何 `complete_opt_x_lb` 键（V8：只有 `bounds_hashes` 下的 `null`）。
- 而 `capture_mpc_state`（`v34:685–704`）对 `opt_x_lb` 用的是 `arr_hash(...) if hasattr(...) else None`，结果也是 null。

两个都空，只有两种可能：(a) do-mpc 的 mpc 对象在这条构造路径上确实没有 `opt_x_lb` 属性；(b) 求解后这些属性被置空/未回填。**无论哪种，`hasattr` 为假都会让 `residual_vs_bounds` 拿到空数组并返回 `None`，而 `None` 又必然触发门失败**（`v34g:175–180` 要求非 None）。所以这条门在当前实现下**即使残差为零也不可能通过**——这是纯粹的仪表缺陷。

修复要求（零求解、零 plant）：
- 捕获时**同时**记录 `opt_x_lb` / `opt_x_lb_num` / `lb_opt_x` 及对应所有可能名，取第一个存在的；并把"哪些名字存在、哪些不存在"写进产物，而不是静默 `null`。
- 残差必须在 `mpc.solve` 返回后**立即在内存中**计算并持久化（数组本体或残差标量二者至少存一个），不要依赖 `raw.json` 落盘后再回捞。
- 若所有名字都不存在，门必须给出 `residual_gate_unavailable_due_to_missing_bounds` 这类**区分性**失败原因，而不是与"残差超限"共用一个字符串。上轮已指出 `None` 被当作通过的问题（`v34:971`），现在暴露出的是反面：`None` 无法通过，但原因不可辨。
